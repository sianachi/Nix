Section: View kinds
- List (list): optional: groupBy (select, checkbox or $type). Rows and columns, one row per child, optionally in sections.
- Board (board): needs a select property. Cards grouped into columns by a single select property.
- Calendar (calendar): needs a date-shaped property. Items placed on a day, week or month by a date property.
- Timeline (timeline): needs a date-shaped property; optional: endDate (date-shaped). Bars across a time axis; without an end date an item is a milestone.
- Gallery (gallery): optional: cover (image). Children as cards, each optionally showing a picture property.
- Spreadsheet (sheet). Children as an editable grid, one row per child and one column per property.
- Form (form). A single-page fillable form over the schema; each submission is a new child.
- Interactive form (interactive_form). A multi-page, conditional form whose answers create a child item.
- Smart list (query). A saved cross-container query, run server-side from stored filters.
- Chart (chart): needs a select property; optional: measureField (number). Children summarised into bars, counted or totalled by a number property.
- Habit tracker (habit_tracker). Habit children arranged by local date with recorded progress.
- Checklist (checklist): optional: doneProperty (checkbox). A box to tick per child, with progress; columns[0] is shown beside each title.
- Matrix (matrix): needs a select or checkbox property; optional: rowBy (select or checkbox, required). Cards in a grid of cells, placed by two properties at once.
- Outline (outline). The subtree as a collapsible tree of titles, reshaped by keyboard.

Section: Recipes
board: Board - Arrange items in columns defined by a select field.
timeline: Timeline - Plan work across start and optional end dates.
gallery: Gallery - Show child items as visual cards with optional covers.
sheet: Spreadsheet view - Edit child items in a property-backed grid.
form: Quick form - Collect authenticated responses in one straightforward page.
interactive-form: Interactive form - Build a multi-page form with branching and an optional public link.
query: Smart list - Find matching items across the workspace with reusable rules.
calendar: Calendar - Place child items on a day, week, or month calendar.
list: List - Show child items and their fields in an ordered list.
checklist: Checklist - Tick child items off one line at a time, with progress.
matrix: Matrix - Place cards in a grid by two select fields, such as urgency and importance.
outline: Outline - Shape the items inside as a tree of titles: add, indent and reorder by keyboard.
habit-tracker: Habit tracker - Track daily or weekday habits with a simple weekly check-in grid.

Section: Query operators
- equals: a literal value, or "me" for the calling principal
- not-equals: a literal value, or "me" for the calling principal
- on: "today", "start-of-week", "start-of-month", "same-day-last-week", "same-day-last-month" or a yyyy-MM-dd date
- before: "today", "start-of-week", "start-of-month", "same-day-last-week", "same-day-last-month" or a yyyy-MM-dd date
- on-or-after: "today", "start-of-week", "start-of-month", "same-day-last-week", "same-day-last-month" or a yyyy-MM-dd date
- within-next: a whole number of days
- within-last: a whole number of days
- contains: text to find, ignoring case; or one multi-select option exactly
- not-contains: text to find, ignoring case; or one multi-select option exactly
- greater-than: a number
- less-than: a number
- is-empty: no value (empty string)
- is-not-empty: no value (empty string)

A formula reads other properties by name in square brackets, as [estimate].
- #DIV/0!: This formula divides by zero.
- #REF!: A formula reads other properties by name in square brackets, as [estimate], and cannot read spreadsheet cells.
- #CYCLE!: This formula refers to itself, directly or through another formula.
- #VALUE!: This formula uses a value of the wrong kind, such as text where a number is needed.
- #NAME?: This formula uses a property name that nothing here declares.
- #LIMIT!: This formula is too long or too involved to finish evaluating.
- #PARSE!: This formula isn't written in a way the parser understands.

Section: Blueprint schema
A blueprint is version 1, a title, a one-paragraph summary, a root node, up to 10 inputs and up to 100 init rules. A node has an id, a title, up to 30 fields, up to 6 views (a node with views is a container), markdown, recurrence, habit settings, values and children. Limits: 40 nodes total, 15 non-sample, depth 4, 80 fields, 20 views, 30 sample entries, 80 planned writes.
Blueprint JSON uses fields shaped as {"label":"Status","type":"select","options":["Open","Done"]}; label and type are required. Do not use name for a field. Put sample or initial field values on a node under values, keyed by field key, for example {"values":{"status":"Open"}}; do not use properties or entries for blueprint node values. A view is shaped as {"kind":"board","groupBy":"status"}; kind-specific settings must match the view kind. On a list, groupBy draws sections from a select, a checkbox or $type (body kind).
Valid view settings by kind:
- list: groupBy
- board: groupBy
- calendar: date
- timeline: date, endDate
- gallery: cover
- sheet: no kind-specific settings
- form: no kind-specific settings
- interactive_form: no kind-specific settings
- query: no kind-specific settings
- chart: groupBy, measureField
- habit_tracker: no kind-specific settings
- checklist: doneProperty
- matrix: columnBy, rowBy
- outline: no kind-specific settings

Section: Patterns
Efficiency patterns

These are the habits that keep a design small: fewest items for the job, fields declared on the
parent so every child inherits them, one container with several views rather than parallel copies
of the same list, a smart list instead of a duplicated set of items, a `formula` or `rollup`
instead of a field the owner has to keep updated by hand, task-semantic types so the machinery
built for them works without extra filters - `due_date` is recurrence's anchor and half of what
the shipped Overdue and Today smart lists match on, `completion` is Overdue's other half - and
`start_date`, `priority` and `estimate` for their plain meaning even where nothing reads them
specially yet. Use recurrence or a `habit_tracker` view for anything repeating, a `form` or
`interactive_form` for capture, a `board` or `calendar` for review, and a `chart` for trends. Every
example below uses only field types, view kinds and operators this build actually has.

Reading log

One container, not one item per book plus a separate list. Fields: "status" (a `select`, the
stages a book moves through), "rating" (a `number`), "started" (a `start_date`), "finished" (a
`due_date`) and "done" (a `completion`) - the pair the shipped Overdue smart list needs, so it and
Today both work on this schema without extra configuration. Two views on the same container: a
`board` grouped by "status" for picking up a book, and a `list` for the whole collection sorted by
when it was finished. No separate "currently reading" item is needed - a `query` view filtering
"status" `equals` "Reading" answers that.

Job hunt

One container for every application, not one board per company. Fields: "stage" (a `select`),
"applied" (a `date`), "follow up" (a `due_date`). Views: a `board` grouped by "stage" for the
pipeline, and a `query` view filtering "follow up" `within-next` 7 to see what needs a nudge this
week - no duplicated "follow up" item alongside each application, and no field to hand-track which
ones are about to come due. A `chart` grouped by "stage" shows the funnel without maintaining
separate counts anywhere.

Meal plan

One container for the week, not one item per day. Fields: "date" (a `date`, the day the meal
lands on), "meal" (a `select`, Breakfast, Lunch or Dinner) and "notes" (`text`) on each entry, with
a `calendar` view placed by "date" so the week reads at a glance, and a `board` grouped by "meal"
as an alternative look at the same data. No `rollup` is needed here because nothing is being
totalled; a grocery list that did total quantities would declare an `estimate` field per
ingredient and a parent `rollup` rather than a field the owner adds up by hand.
