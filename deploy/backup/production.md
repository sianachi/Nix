# Production backups

The operator guide to backing up and restoring the production Compose host. It covers what is
captured, where the copies live, how to tell the system is healthy, and how to get data back.
Day-to-day setup commands are also in [deploy/README.md](../README.md#off-host-backups); this
guide is the one place that explains the whole system. `scripts/backup-r2.py` and
[README.md](README.md) in this directory are the separate tool for the local development stack.

## At a glance

| | Release backup | Nightly backup |
| --- | --- | --- |
| Taken by | `release.sh`, before any writer stops | `nix-backup-nightly.timer`, about 02:30 local |
| Local copy | `~/nix-backups/pre-<sha>` | `~/nix-backups/nightly-<UTC stamp>` |
| Local retention | `prune.sh` keeps the current and previous release | `nightly.sh` deletes copies older than 7 days |
| Off-host copy | restic snapshot tagged `kind=release`, `sha=<sha>` | restic snapshot tagged `kind=nightly` |
| Off-host retention | last 10 | 7 daily, 4 weekly, 6 monthly |
| On failure | Release stops before writers stop (`NIX_OFFSITE_REQUIRED=1`) | Later steps skipped, logged, marker not updated |

Off-host copies live in the restic repository `restic/nix-production` in the `nix-backup` R2
bucket. The development stack uses `restic/nix-local` in the same bucket; the two never mix.

## What each backup contains

Every backup directory is mode 700; every file in it is mode 600.

| File | What it is |
| --- | --- |
| `nix.dump` | `pg_dump -Fc` of the `nix` database, taken from an exported snapshot |
| `roles.sql` | `pg_dumpall --roles-only` (includes password hashes) |
| `zitadel.dump`, `zitadel-roles.sql` | The Zitadel identity database and its roles, when Zitadel runs |
| `nix-versity-data.tar` | Attachments and object storage; Versity is paused for the archive |
| `nix-api-data-protection.tar` | ASP.NET data-protection keys (sign-in cookies and protected data) |
| `nix-companion-data.tar` | Companion data |
| `env.private` | The production env file: every application secret |
| `core-access-token.pem` | Core's access-token signing key |
| `compose.prod.yml`, `Caddyfile.prod` | The manifest and edge config the running stack was started from |
| `containers.private.json` | `docker inspect` of the running containers |
| `SHA256SUMS`, `verified.txt` | Checksums, and the outcome of the restore check |

A backup directory is a complete set of production secrets. Treat it like the env file itself.

### What is deliberately not captured

- **`nix-postgres-data`**: the raw data directory. The logical dump replaces it and restores
  across Postgres builds.
- **`nix-opensearch-data`**: search is derived from the database and rebuildable. After a
  restore, search stays incomplete until it is re-indexed. Re-indexing is not scripted yet, so
  check search results after any restore.
- **`nix-rabbitmq-data`**: a transport, not a record. Events are written to the database outbox
  (`worker_outbox_event`) before they are published, so the database is authoritative.
- **`nix-caddy-data`, `nix-caddy-config`**: regenerated by Caddy. The public edge is the
  Cloudflare tunnel, whose token is in the env file.
- **`nix-loki-data`, `nix-alloy-data`, `nix-grafana-data`**: observability history. Losing it
  loses old logs and metrics only.

## How a backup is verified

`backup.sh` does not trust a backup it has not restored. After writing the files it:

1. checks every file against `SHA256SUMS`
2. restores the roles and `nix.dump` into a throwaway `--network none` pgvector container
3. compares the table count, and the row counts of the ten largest tables, with the counts
   recorded inside the same database snapshot the dump used. They must match exactly, so a
   mismatch is a real fault, never a side effect of users writing during the backup.
4. restores the Zitadel dump into a second throwaway container, and compares its table count
5. compares each volume archive's file count with the live volume. The companion volume changes
   constantly, so a difference there is only a warning.
6. records the outcome in `verified.txt`

`backup.sh --check <dir>` passes only when every expected file is present, the checksums still
match, the modes are private, and `verified.txt` records a passed restore for exactly these
files. `deploy.sh` will not start without a backup that passes it, and `offsite.sh push` will not
upload one that fails it. Backups made before Zitadel capture are accepted, with a note.

The first real runs, on 2026-09-25: a backup was about 313 MiB, the first R2 push took about
1.5 minutes, and a restore from R2 passed `--check` and restored the database intact.

## Health checks

Run these on the host (each is read-only apart from `check`'s repository lock):

```sh
# When did the last nightly succeed?
cat ~/nix-production/last-nightly-success
systemctl --user list-timers nix-backup-nightly.timer
journalctl --user -u nix-backup-nightly.service --since yesterday

# What is off-host?
bash ~/nix-production/backup-tools/offsite.sh snapshots

# Is the repository sound? Monthly: read a sample of the stored data too.
bash ~/nix-production/backup-tools/offsite.sh check
bash ~/nix-production/backup-tools/offsite.sh check --read-data-subset=5%

# Is a local copy intact?
bash ~/nix-production/backup-tools/backup.sh --check ~/nix-backups/<dir>
```

`release.sh` also reads the marker. Its plan warns, without stopping the release, when no
nightly has succeeded or the last success is older than 36 hours (`NIX_NIGHTLY_MAX_AGE_HOURS`).
A failing timer therefore surfaces at the next release at the latest. Until the marker feeds an
alert in Grafana, check it by hand after any host change.

Rehearse a restore from R2 at least once a quarter, following "Check a snapshot from R2" below.
A backup that has never been restored is a hope, not a backup.

## Restore

Always restore into isolation first. Never extract a backup over a running production volume.

### Check a snapshot from R2

```sh
bash ~/nix-production/backup-tools/offsite.sh snapshots
bash ~/nix-production/backup-tools/offsite.sh restore <snapshot-id> /absolute/empty/dir
bash ~/nix-production/backup-tools/backup.sh --check /absolute/empty/dir/backup/<pre-sha-or-nightly-stamp>
```

The restored tree belongs to the operator and can be removed with `rm -rf`. It holds production
secrets, so remove it when you are done.

### Recover production on this host

A restore replaces current data with the backup's, and everything written since the backup is
lost. It has not yet been rehearsed end to end on a live host, so read it through before starting
and keep the old volumes until the restored service is proven.

1. **Choose the backup.** Use the newest local one if it passes `--check`; otherwise restore one
   from R2 as above.
2. **Take a backup of the current state** with `backup.sh` if the database still runs, so the
   restore itself can be undone.
3. **Stop the writers.** Run the `stop` line from `deploy.sh`, or stop the whole `nix` project.
4. **Restore the database** into a fresh cluster. Create a new, empty `nix-postgres-data` volume
   under a new name (keep the old one), start Postgres on it, then:
   `psql -f roles.sql`; `createdb nix --owner nix_migrator`; `pg_restore -d nix --exit-on-error nix.dump`.
   Keep ownership, unlike the verification restore, which uses `--no-owner`: row-level security
   and grants depend on it.
5. **Restore the volumes.** For each archive, restore into an empty volume, for example
   `docker run --rm --network none -v <volume>:/data -v <backup-dir>:/in:ro pgvector/pgvector:pg16 tar -C /data -xf /in/<volume>.tar`.
6. **Restore secrets and keys** only if they are lost: `env.private` becomes the production env
   file, and `core-access-token.pem` goes to the path the env file names. Restoring an older
   data-protection key signs every user out; that is expected.
7. **Start the stack** with `deploy.sh`, pointing `NIX_BACKUP_REFERENCE` at the backup you took in
   step 2. Then run the smoke checks and the browser checks from the runbook, and check search.
8. **Restore Zitadel** the same way, in its own Compose project (`~/zitadel`), only if its
   database was lost.

### Rebuild on a new host

A replacement host needs, before the steps above:

- the host prerequisites from [deploy/README.md](../README.md#prerequisites-and-configuration)
- Docker with the operator in the `docker` group, and linger enabled
- `~/nix-production/backup.env`, rebuilt from the password manager and the R2 credentials. The
  restic password cannot be recovered from anywhere else.

Then restore the newest snapshot from R2, follow "Recover production on this host", and install
the nightly timer again as described in [deploy/README.md](../README.md#off-host-backups).

## Credentials

| Secret | Lives in | If lost |
| --- | --- | --- |
| Restic password | `backup.env` on the host, and the password manager | Every off-host snapshot is unreadable |
| R2 access key | `backup.env`; also used by the dev-stack job on the operator's Mac | Mint a new bucket-scoped key |
| Application secrets | `~/nix-production/production.env` (copied into every backup) | Restore from a backup |

- **Rotate the R2 key** by minting a new key scoped to `nix-backup` (Object Read & Write), then
  replacing the two `AWS_` lines in `backup.env`. Run `offsite.sh snapshots` to prove the new key
  works, then revoke the old one.
- **Never replace the restic password.** To change it, add a second key to the repository, prove
  it works, then remove the old one. Record the new password before removing anything. `offsite.sh`
  has no subcommand for this; run restic directly with the same image and credentials file, and
  have it prompt for the new password rather than putting it on the command line:

  ```sh
  restic() { docker run --rm -it --env-file ~/nix-production/backup.env restic/restic:0.19.1@sha256:136600b6ff6843d61d355f7f71f460a166429f35de6fd11b568fece3c9a4d510 "$@"; }
  restic key add        # prompts for the new password
  restic key list       # note the old key's ID
  # put the new password in backup.env and the password manager, then prove it:
  bash ~/nix-production/backup-tools/offsite.sh snapshots
  restic key remove <old-key-id>
  ```
- **`backup.env`** must be owned by the operator, mode 600, and hold exactly `RESTIC_REPOSITORY`,
  `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_DEFAULT_REGION`.
  `offsite.sh` refuses anything else, and never prints, sources or copies it.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `nightly: this process is not in the docker group` | The systemd user manager started before the operator joined `docker`. Run `sudo systemctl restart user@$(id -u).service`, or reboot. |
| The timer never fires overnight | Linger is off. Run `sudo loginctl enable-linger "$USER"`. |
| No nightly logs after a reboot | The journal is in memory only. Make `/var/log/journal` persistent as in the runbook. |
| `Fatal: unable to open config file: Stat: Access Denied` | R2 refused the key: it was revoked, is scoped to another bucket, or R2 had a transient fault. Run `offsite.sh snapshots`; if it fails, check the key in the Cloudflare dashboard. |
| `repository is already locked` | A previous restic run was killed. Confirm no backup is running (`pgrep -f restic`), then remove the stale lock: `docker run --rm --env-file ~/nix-production/backup.env restic/restic:0.19.1@sha256:136600b6ff6843d61d355f7f71f460a166429f35de6fd11b568fece3c9a4d510 unlock`. |
| `backup.sh` fails on row counts | A real mismatch between the dump and its snapshot. Do not use that backup; rerun, and investigate if it repeats. |
| `release.sh` stops with `failed:offsite` | The push failed and `NIX_OFFSITE_REQUIRED=1`. Fix R2 and rerun with `NIX_BACKUP_REFERENCE` set to the backup it made, or set `NIX_OFFSITE_REQUIRED=0` for that release only. |
| A restored tree cannot be deleted | It was restored by a version of `offsite.sh` from before 2026-09-25. Remove it through a container: `docker run --rm -v <parent>:/h <image> rm -rf /h/<dir>`. |
